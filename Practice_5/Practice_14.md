## 1. Выбор транзакционно критичных операций

### Операции

| Операция                     | Изменяемые данные                  | Причины атомарности                                   |
|------------------------------|------------------------------------|------------------------------------------------------|
| Изменение статуса заявки      | Статус заявки                      | Нельзя менять статус без обновления связанной информации |
| Закрытие наряда              | Статус наряда, исполнители        | Закрытие без обновления исполнителей ведет к несоответствию |
| Назначение исполнителя        | Исполнитель, статус заявки         | Исполнитель должен соответствовать статусу            |
| Изменение данных пользователя  | Данные пользователя                | Нельзя частично обновлять данные                      |

### Последствия частичного выполнения

- Изменение статуса без обновления исполнителя может привести к конфликтам при выполнении задач.
- Закрытие наряда без соответствующих обновлений может привести к утере информации и неверным отчетам.

---

## 2. Определение границ транзакции

### Начало и конец транзакции
- **Начало**: Транзакция начинается перед первой обновляющей операцией.
- **Конец**: Транзакция заканчивается после успешного завершения всех операций или при возникновении ошибки.

### Запрещенные внешние вызовы
- Внешние API-вызовы запрещены, так как результаты могут не соответствовать транзакционным операциям.

### Подход к компенсации
- Если часть операций выполнена, необходимо создавать механизм для отката изменений. Например, если статус изменен, его нужно вернуть в предыдущие значение.

---

## 3. Выбор уровней изоляции и обоснование

### Уровни изоляции для операций

| Операция                     | Выбранный уровень изоляции | Обоснование                                         |
|------------------------------|----------------------------|-----------------------------------------------------|
| Изменение статуса заявки      | Serializable               | Предотвращает грязные чтения и фантомы             |
| Закрытие наряда              | Repeatable Read            | Запрещает неповторяемое чтение                     |
| Назначение исполнителя        | Serializable               | Защита от конфликтов с другими назначениями          |
| Изменение данных пользователя  | Read Committed             | Минимальные накладные расходы, допустимо грязное чтение |

### Аномалии
- Запрещены: грязные чтения, фантомы, неповторяемые чтения для критичных операций.
- Допускаются: для не критичных операций.

## 4. Реализация конкурентного контроля

### Оптимистическая блокировка
- Реализация через поле версии записи.

### Обработка конфликтов
- Если версия записи не совпадает, операция не выполняется и пользователю показывается сообщение о конфликте.

### Требования к операциям
- **Строгий контроль**: Изменение статуса заявки, назначение исполнителя.
- **Мягкие гарантии**: Изменение данных пользователя.

---

## 5. Параллельные сценарии и тесты конкурентности

### Сценарии

| Сценарий                    | Описание                                                  | Ожидаемый результат                                   |
|-----------------------------|----------------------------------------------------------|-------------------------------------------------------|
| Двойное закрытие наряда     | Два пользователя пытаются закрыть один и тот же наряд  | Запрет второго закрытия                               |
| Изменение статуса одновременно | Два пользователя изменяют статус одной заявки           | Статус меняется корректно, ошибка для другой       |
| Назначение исполнителя параллельно | Два исполнителя назначаются на один и тот же заказ    | Последний назначенный сохраняется, первый отклонен   |
| Изменение данных одновременно | Изменение данных пользователем и администрацией         | Данные обновляются без конфликтов                     |
| Сопоставление статусов      | Один пользователь меняет статус, другой - назначает исполнителя | Выполнение операций согласно правилам                 |

### Результаты тестов
- Все операции выполняются корректно, данные остаются целостными.

## 6. Использование расширенного SQL

### Примеры запросов

```sql
WITH UpdatedTickets AS (
    UPDATE Tickets
    SET Status = 'Closed'
    WHERE Id = @ticketId
    RETURNING *
)
SELECT * FROM UpdatedTickets;
```

### Обоснование
- Использование CTE упрощает логику и минимизирует количество запросов. 
- Безопасно при параллельности, так как изменения видимы только после завершения транзакции.

## 7. Диагностика блокировок и взаимных ожиданий

### Возможные блокировки
- Эксклюзивные блокировки на записи, когда данные обновляются.

### Правила таймаутов
- Таймаут выполнения транзакции не более 30 секунд.

### Метрики и логи
- Логи блокировок, время выполнения операций, количество неудачных попыток выполнения.

## 8. Метрики и критерии оценки корректности

### Метрики

| Метрика                         | Значение                |
|---------------------------------|------------------------|
| Доля конфликтов версий          | < 5%                   |
| Средняя длительность транзакции  | < 200 мс               |
| Число ретраев                   | < 3 на 100 операций    |

### Пороги деградации
- Если доля конфликтов больше 5%, система считается деградирующей.

### Действия при превышении порогов
- Уведомление администраторов, временная блокировка операций.

## 9. Рекомендации по эксплуатации транзакционного контура

### Настройки пула соединений
- Рекомендуется настраивать пул соединений с лимитом 100.

### Индексы и статистика
- Индексы на поля, участвующие в WHERE, JOIN и ORDER BY.

### Обновление схемы БД
- Использовать миграции для обновлений, избегая блокировок с помощью фоновых операций.
